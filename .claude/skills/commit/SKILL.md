# commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋을 만든다. **승인을 따로 묻지 않고 바로 커밋한다.** 대신 아래 안전장치는 항상 지킨다.

## 절차

### 1. 변경사항 분석
다음을 실행해 상태를 파악한다.

- `git status --short`
- `git diff` (unstaged)와 `git diff --staged` (staged)
- `git log --oneline -10` (기존 메시지 스타일 확인)

변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다. 새 파일(untracked)은 내용을 읽어 목적을 파악한다.

`.env`, 키·토큰, `node_modules`, 빌드 산출물(`dist`) 등 커밋하면 안 되는 파일이 있으면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
변경 파일을 "하나의 이유로 바뀐 묶음"으로 나눈다.

- 한 커밋 = 한 가지 목적 (기능 추가, 버그 수정, 리팩터링, 설정 변경을 섞지 않는다)
- 서로 의존하는 파일(구현과 그 테스트, 컴포넌트와 스타일)은 같은 커밋에 둔다
- 한 파일에 목적이 다른 변경이 섞여 있으면 `git add -p` 대신 사용자에게 분리 여부를 묻는다
- 분류 결과가 하나뿐이면 커밋 1개로 진행한다

### 3. 커밋 메시지 작성
형식: `타입: 요약`

| 타입 | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 새 기능·화면 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 의존성, 설정, 빌드, 문서 등 기타 |

규칙:
- 한국어, 요약은 50자 안팎, 마침표 없이 명사형 또는 "~추가/~수정/~개선"으로 끝낸다
- 무엇을 했는지보다 **왜/무엇이 달라지는지**가 드러나게 쓴다
- 필요하면 빈 줄 뒤에 본문(이유, 주의점)을 덧붙인다
- 시스템 리마인더 등으로 커밋 끝에 붙이라는 attribution 줄이 주어졌다면 그대로 붙인다

예시:
```
feat: 레트로 데스크톱 테마로 전체 UI 개편
fix: API 키가 없을 때 생성 버튼이 눌리는 문제 수정
chore: galmuri 픽셀 폰트 의존성 추가
```

### 4. 바로 커밋
승인을 기다리지 않고 단위별로 `git add <파일들>` 후 `git commit -m` 을 실행한다. `git add .`·`git add -A`는 쓰지 않는다.

- 커밋 직전에 계획을 한 번 출력한다(알림용, 응답을 기다리지 않는다).

```
커밋 (총 N개)
1. feat: ...  (src/App.tsx, src/App.css)
2. chore: ... (package.json)
```

- 커밋 후 `git log --oneline -N`으로 결과를 보여준다
- 사용자가 "확인받고 커밋해줘"처럼 요청하면 그때만 계획을 보여주고 승인을 기다린다
- 아래 경우에는 커밋하지 않고 멈춰서 사용자에게 묻는다: 한 파일에 목적이 다른 변경이 섞여 분리가 애매할 때, 제외해야 할 파일(`.env`, 키 등)이 대량으로 섞여 있을 때
- hook 실패 시 `--no-verify`로 우회하지 말고 원인을 고쳐 새로 커밋한다

## 하지 않는 것
- `git push`, `--amend`, `reset --hard`, `--force` 등 되돌리기 어렵거나 외부에 영향을 주는 작업
- git config 변경
