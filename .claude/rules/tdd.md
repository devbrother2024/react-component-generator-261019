# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다. 이 파일은 **기본값(fallback)** 이다. 충돌하는 항목만 프로젝트 규칙을 따르고, 나머지는 이 파일을 따른다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**: 계산, 판단, 상태 전이, 데이터 변환
- **API**: 핸들러, 요청 검증, 응답·에러 매핑
- **유틸 / 순수 함수**: 파싱, 포매팅, 정규화
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다

### TDD가 불필요하다

- **타입 정의**: `interface`, `type` 선언만 있는 파일
- **설정 파일**: `tsconfig`, `vite.config`, `eslint` 등
- **순수 UI**: 로직 없는 마크업·스타일링 (로직이 섞이면 로직 부분은 적용 대상)
- **SQL**: 스키마, 마이그레이션 정의

판단이 애매하면 **적용 대상으로 본다.**

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 않는다
- 테스트 이름은 기대 동작을 서술한다
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 테스트를 고쳐 다시 실행한다

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다
- **YAGNI**: 아직 테스트가 요구하지 않는 기능, 옵션, 분기를 넣지 않는다
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다
- **모든 테스트가 green인 상태를 유지**한다. 변경 후마다 실행한다
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구사항의 모든 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. RED(실패하는 테스트)부터 다시 시작한다.

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 안 된다
- 삭제한 코드를 보며 다시 쓰지 않는다. 테스트가 요구하는 대로 새로 작성한다

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드도 깨진다. 테스트는 30초면 쓴다. 단순할수록 비용이 낮으니 안 쓸 이유가 없다 |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 이미 통과하는 코드에 맞춰 쓰게 되어 아무것도 증명하지 못한다. 그리고 "나중"은 오지 않는다 |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 회귀 수정에 더 많은 시간을 쓴다. 급할수록 테스트가 시간을 번다 |
| 삭제하면 낭비 | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 더 큰 비용이다. 삭제 후 재작성은 더 빠르고 더 단순하다 |
| 프로토타입이다 | 프로토타입은 프로덕션이 되는 경우가 대부분이다. 버릴 코드라면 테스트도 버리면 되니 손해가 없다 |
